Статический семейный сайт для GitHub Pages: главная, интерактивное древо, личные страницы с родственниками и хронологией, документальный архив.

Это техническое руководство. Семейные сведения и расхождения источников храните в данных людей и документов; их изменения попадают на сайт при следующей сборке.

| Где хранится | Назначение |
| --- | --- |
| `src/data/family.json` | Имена, основные даты, родственные связи и замечания к семейным данным |
| `src/data/people/` | Биографии, фотографии, места, события и ссылки на источники |
| `src/data/documents/` | Описания документов, расшифровки, архивные реквизиты и связанные люди |
| `src/data/places/` | Названия и административная принадлежность мест |
| `public/media/sources/` | Тексты семейных воспоминаний и выписки из внешних источников |
| `public/media/documents/` | Сканы, PDF и облегчённые превью документов |
| `public/media/photos/` | Фотографии для личных страниц |

Тексты в `public/media/sources/` отражают содержание источников. Уточнения вносите в семейные данные и профили, а существенные расхождения поясняйте в `notes`. Документы не меняют имена, даты или родственные связи автоматически. `src/data/sources/` хранит метаданные источников; сейчас загрузчик не использует этот каталог, а ссылки для сносок берёт из `sources` профилей.

## 1. Запустить сайт локально

Установите [Node.js](https://nodejs.org/) версии 24; npm устанавливается вместе с ним. Откройте терминал в папке проекта:

```sh
cd "/путь/к/Family tree"
npm install
npm run dev
```

Откройте напечатанный адрес, обычно `http://127.0.0.1:4321/`. При сохранении файлов страница обновляется. Чтобы остановить сайт, нажмите Ctrl+C.

Перед публикацией:

```sh
npm test
npm run build
```

Готовый статический сайт находится в `dist/`. Для просмотра сборки выполните `npm run preview`.

## 2. Добавить или исправить человека

Откройте `src/data/family.json`. В массиве `people` каждый объект — отдельный человек:

```json
{
  "id": "new-person",
  "firstName": "Имя",
  "lastName": "Фамилия",
  "patronymic": "Отчество",
  "maidenName": "",
  "birthYears": [],
  "deathYears": []
}
```

Это шаблон, а не семейные сведения. Заполните его реальными данными. `id` уникален и состоит из латинских строчных букв, цифр и дефисов. После появления ссылок не меняйте ID: он используется для родства и адреса `/people/new-person/`.

Формат семейного файла — `"schemaVersion": 2`. Вместо общей строки `name` у каждого человека четыре обязательных поля: `firstName` — имя, `lastName` — фамилия, `patronymic` — отчество, `maidenName` — девичья фамилия. Неизвестные фамилию, отчество или девичью фамилию обозначайте пустой строкой `""`; имя должно быть заполнено. Сайт собирает полное имя в порядке «Имя Отчество Фамилия». Девичья фамилия отдельно показывается на личной странице и участвует в поиске. Родственные связи сами по себе не заполняют части имени.

В этом семейном архиве имя отца определяйте по известному отчеству ребёнка: например, Герасимовна — Герасим, Николаевич — Николай. Если отец ещё не записан, добавьте его с известным именем и связью `parent`, `role: "father"`, `status: "explicit"`. На страницах показывайте имя и родство без пояснений о происхождении имени из отчества. Фамилию, собственное отчество и даты отца заполняйте только при наличии отдельных сведений. Используйте поле `patronymic`; фамилия или неразобранное архивное имя сами по себе не заменяют отчество. Совпадение имени не означает, что отца нужно объединять с уже существующим человеком.

Если архивная запись не позволяет отличить фамилию от исторической формы отчества, сохраните полное написание в необязательном поле `archivalName`, а неясные части оставьте пустыми. При наличии `archivalName` оно используется для имени на древе, в списке людей, на личной странице и в метаданных. Поиск учитывает и архивное написание, и заполненные части имени. На личной странице появляется пометка «Имя сохранено в архивном написании». Не заменяйте архивную форму современным отчеством без подтверждения.

Пустой массив означает неизвестный год. Один год: `"birthYears": [1889]`. Несколько допустимых вариантов: `"birthYears": [1794, 1795]`. Не выбирайте один вариант без основания.

Можно также использовать поля `birth` и `death` непосредственно в исходной записи. Они принимают `YYYY`, `YYYY-MM`, `YYYY-MM-DD` или `null`; точность сохраняется. Например, `"birth": "1969-03-18"` и `"death": null`. Для одного события укажите только одно представление: `birth` **или** `birthYears`, `death` **или** `deathYears`.

Не копируйте те же даты в `birthDate` и `deathDate` профиля человека: дата уже берётся из `family.json`. Поля дат в профиле нужны только для более точного уточнения, например день и месяц при известном в семейном файле годе. Не добавляйте пустые `null` ради заполнения шаблона — отсутствие необязательного поля означает то же самое.

Для людей с годом рождения от 1935 включительно, у которых нет указанной даты или вариантов года смерти, сайт показывает `род. 1969` вместо `1969 — ?`. На личной странице пустая строка «Смерть» не показывается. Если год рождения имеет несколько вариантов, это правило действует, только когда все они от 1935 года. Известные даты и варианты года смерти остаются в отображении. Правило применяется к древу, спискам, личным страницам и метаданным; исходные даты сохраняются, статус человека автоматически не устанавливается.

Необязательный массив `alternateNames` хранит другие варианты имени, например `"alternateNames": ["Ксения Михеева"]` для Ксении Михайловой. Они отображаются на личной странице и участвуют в поиске людей и документов; отдельные узлы для них не создаются.


Для биографии, фото и дополнительных сведений создайте необязательный профиль в `src/data/people/tree/` для людей, показанных отдельными узлами основного древа при текущем фокусе, или в `src/data/people/non-tree/` для остальных записей. Люди, доступные только через раскрывающиеся списки родственников, относятся к `non-tree/`. Если фокус или состав основной схемы изменится, при необходимости переместите профили между папками. Если имя и год рождения установлены однозначно, используйте имя и год в имени файла, например `petr-1889.json`. Внутреннее поле `id` при переименовании файла не меняйте: связь профиля с человеком строится по нему. Файлы людей с неизвестными или спорными годами рождения пока оставляйте без переименования.

```json
{
  "id": "new-person",
  "summary": "Краткое описание.",
  "biography": "Известные сведения о жизни."
}
```

Это шаблон профиля для человека из предыдущего примера. Добавляйте только известные дополнительные сведения. Для места рождения используйте `birthPlaceId` с ID из `src/data/places/`; при неизвестном месте поле можно опустить.

Такой профиль дополняет существующий узел; новый человек должен сначала появиться в `family.json`. В профиле не дублируются родители, дети или супруги.

Допустимые дополнительные поля профиля:

- `slug` — отдельная уникальная часть адреса, если нужна вместо ID.
- `sex` — `male`, `female`, `unknown`; без указания пол не угадывается.
- `birthDate`, `deathDate` — уточнённая дата `YYYY`, `YYYY-MM`, `YYYY-MM-DD`, либо `null`.
- `birthPlaceId`, `deathPlaceId` — ID места или `null`.
- `birthDocumentId`, `deathDocumentId` — ID документа, подтверждающего рождение или смерть. Документ должен быть связан с этим человеком через `peopleIds`.
- `portrait`, `summary`, `biography`, `notes`, `marriages`, `events`, `sources`.

Точная дата должна согласовываться с единственным годом в исходной записи. При нескольких вариантах годов нельзя выбрать дату в профиле молча: сначала уточните `family.json` и сохраните объяснение в `issues`. Не подставляйте вымышленный месяц/день. Переносы абзацев внутри строки JSON пишутся как `\n\n`.

Короткую `biography` можно оставить строкой. Развёрнутую биографию разбейте на массив тематических пунктов с заголовком `title` и текстом `text`:

```json
{
  "biography": [
    { "title": "Образование", "text": "Сведения об учёбе из источника." },
    { "title": "Профессия и работа", "text": "Известные занятия и места работы." },
    { "title": "Военная служба", "text": "Подтверждённые сведения о службе." }
  ]
}
```

Добавляйте только пункты, для которых есть сведения: например, «Семья», «Хозяйство», «Награды», «Семейные воспоминания». Порядок пунктов в массиве определяет порядок на странице. Заголовок и текст каждого пункта должны быть непустыми; если биография неизвестна, не указывайте поле. Неопределённости и неизвестные даты записывайте в `notes`; ссылки на источники оформляйте сносками, как описано в разделе 4.

Для удобного чтения JSON длинный текст можно записать массивом коротких строк:

```json
{
  "text": [
    "Первая часть длинного предложения",
    "и его продолжение на следующей строке файла."
  ]
}
```

При загрузке строки соединяются одним пробелом, поэтому переносы в файле не меняют текст на сайте. Этот формат поддерживается в `summary`, `notes`, текстовой `biography`, поле `text` разделов биографии и `notes` событий и браков. Переносы абзацев сохраняйте как `\n\n` внутри строки. В файлах `src/data/people/tree/*.json` и `src/data/people/non-tree/*.json` придерживайтесь ширины до 100 символов.

Места хранятся в отдельных файлах `src/data/places/*.json`. В `name` указывайте только современное название населённого пункта; район, регион и страну храните отдельно. Неизвестные административные единицы оставляйте пустыми. Поля `born` и `buried` содержат ID людей, родившихся или захороненных в этом месте; если записей нет, используйте пустой массив. При наличии прежних названий укажите их в `previousNames`; они показываются отдельной строкой на личных страницах:

```json
{
  "id": "place-id",
  "name": "Современное название",
  "district": "Район или пустая строка",
  "region": "Регион или пустая строка",
  "country": "Страна или пустая строка",
  "previousNames": ["Прежнее название"],
  "born": ["person-id"],
  "buried": []
}
```

## 3. Добавить родство

В массиве `relations` файла `family.json` укажите связь один раз. Все связи используют ID существующих людей.

Родитель и ребёнок:

```json
{ "type": "parent", "parent": "parent-id", "child": "child-id", "status": "explicit" }
```

Супруги:

```json
{ "type": "spouse", "person1": "first-id", "person2": "second-id", "status": "explicit" }
```

Это шаблоны: замените ID реальными. Обратные связи, списки детей/родителей/супругов и страницы создаются автоматически. Разрешены несколько родителей и несколько супругов. Если родитель неизвестен, не создавайте вымышленного человека.

Статусы сохранены из исходного файла:

- `explicit` — связь прямо указана в семейных данных.
- Если `status` отсутствует, переданная связь считается `explicit`.
- `inferred_context` — предположение из контекста.
- `inferred_branch_context` — предположение по контексту ветви.
- `unresolved` — вопрос пока не разрешён.

Предполагаемые связи отмечены на личных страницах и пунктирными линиями в древе. При необходимости добавьте `notes`. У родительской связи можно указать `role` (`mother`, `father`, `parent`) и `kind` (`biological`, `adoptive`, `unknown`). Биологический вид родства не выводится автоматически.

Братья/сёстры, для которых неизвестно, один или оба родителя общие:

```json
{ "type": "sibling", "person1": "first-id", "person2": "second-id", "status": "explicit" }
```

Связь сохраняется в обе стороны и показывается с пометкой «Общие родители не уточнены». Она не добавляет родительских записей. Используйте `half_sibling`, когда неполнородное родство установлено:

```json
{ "type": "half_sibling", "person1": "first-id", "person2": "second-id", "status": "explicit" }
```

Возможное совпадение двух исторических записей:

```json
{ "type": "possible_same_person", "person1": "first-id", "person2": "second-id", "status": "unresolved" }
```

Оба человека остаются отдельными. Не объединяйте их по похожим именам.

После подтверждённого объединения записей сохраняйте прежние адреса через `src/data/person-redirects.json`: `from` задаёт старый slug, `personId` — ID оставшейся записи. Для старого адреса генерируется статическая страница с перенаправлением, ссылкой и canonical основной страницы. Проверка отклоняет неизвестные цели, повторы и конфликты с действующими адресами людей.

Для родственников без установленных имён используйте `unidentifiedRelatives`. Сохранены поля `people` (связанные IDs), `relation` (`child` или `possible_additional_child`), `sex`, `count`, `status` (`explicit`, `uncertain`, `conflicting_source`) и необязательное `reason`. Эти сведения показываются в древе и на страницах связанных людей без создания вымышленных карточек.

Массив `issues` хранит замечания: `name_correction`, `date_correction`, `death_year_conflict`, `identity_conflict`, `children_count_conflict`. Укажите `person` или `people`, пояснение `reason`, при необходимости `values`, `preferred`, `relatedPerson`. История исправлений имени и дат остаётся в исходных данных; на личных страницах показываются только неразрешённые вопросы.

Биографии и краткие описания карточек предназначены для широкой аудитории: излагайте сведения о жизни человека ясно и без избыточных оговорок. Все неопределённости, неизвестные имена и даты, предположения, расхождения источников и замечания о необходимости проверки записывайте в `notes`; на личной странице они вынесены в раздел «Примечания». Не превращайте предположение в факт при сокращении текста: целиком предположительные утверждения переносите в `notes` вместе с пояснением и источником. Сохраняйте существенную атрибуцию семейных воспоминаний и документов.

Не публикуйте служебные пояснения о предоставлении файлов пользователем, локальных папках, загрузке, создании и объединении записей, изменении полей или уже выполненных исправлениях. Существенные расхождения и неизвестные обстоятельства описывайте кратко, без отчёта о работе с данными. Редакционные правила для последующих изменений закреплены в `AGENTS.md` в корне проекта.

## 4. Добавить документ и прикрепить его к нескольким людям

Источники на личных страницах показываются сносками: надстрочные номера ведут к списку «Источники» внизу страницы. Массив `sources` сохраняет название, ссылку и страницы каждого источника. Для конкретного раздела биографии можно добавить `"sourceRefs": [1]`: номер отсчитывается от 1 в массиве `sources` этого человека. Несуществующие и повторяющиеся номера отклоняются проверкой данных. Документы событий хронологии и ссылки внутри текста получают сноски автоматически; один источник используется повторно без дублирования.

Сохраните настоящий скан в `public/media/documents/`. Создайте один JSON-файл в `src/data/documents/`:

```json
{
  "id": "document-id",
  "title": "Название документа",
  "type": "other",
  "date": null,
  "peopleIds": ["petr-mikheev-1889"],
  "files": [{ "path": "/media/documents/scan.jpg", "label": "Скан документа" }],
  "archive": { "name": "", "fond": "", "opis": "", "delo": "", "page": "" },
  "transcription": "",
  "notes": ""
}
```

Это шаблон, не утверждение о наличии источника. Укажите реальные сведения и людей, которых источник упоминает. Для общего документа добавьте несколько IDs в `peopleIds`. Документ хранится один раз и автоматически появляется на всех связанных личных страницах и в общем архиве. Правила включения в хронологию описаны в разделе 6.

У скана можно указать необязательное поле `preview` с локальным путём, например `"preview": "/media/documents/previews/scan.webp"`. Оно используется для просмотра и миниатюры, а `path` всегда ведёт на полный оригинал. Проверка данных проверяет наличие обоих файлов. Выписку и фотографию той же записи добавляйте в массив `files` одного документа.

Типы: `metric` — метрические записи, `marriage` — брак, `birth` — рождение, `death` — смерть, `census` — переписи/ревизии, `military` — военные документы, `photograph` — фотографии, `other` — прочее.

Разрешены несколько сканов и PDF. Для внешнего оригинала добавьте `originalUrl` с HTTPS-адресом. Если скана пока нет, допустим `files: []`; отсутствие оригинала будет указано. Документ получает страницу `/documents/<id>/` с архивной ссылкой, расшифровкой и комментариями.

Пути начинаются с `/media/`, без `public` и без названия репозитория. Имена файлов пишите латиницей, с цифрами, дефисами или подчёркиваниями. Префикс GitHub Pages добавляется автоматически.

## 5. Добавить фотографию

Сохраните фото для аватара профиля в `public/media/photos/logos/`. Создайте или дополните профиль нужного человека:

```json
{
  "id": "petr-mikheev-1889",
  "portrait": "/media/photos/logos/portrait.jpg"
}
```

При отсутствии фото оставьте `portrait: null` или не добавляйте поле. Общую фотографию можно оформить как документ типа `photograph` с несколькими `peopleIds`.

## 6. Добавить датированный брак или другое событие

Хронология вычисляется автоматически. Для известного события брака внесите `marriages` в профили обоих супругов, указав у каждого ID другого человека:

```json
{
  "marriages": [
    { "spouseId": "second-id", "date": "1950" }
  ]
}
```

Это шаблон: замените дату и ID сведениями о нужной паре. Связь супругов должна уже быть в `family.json`. Дата и необязательный `documentId` совпадают в обоих профилях; документ должен упоминать обоих. Сохраняйте точность даты: `YYYY`, `YYYY-MM` или `YYYY-MM-DD`; при неизвестной дате используйте `null`. Несколько браков поддерживаются. Свадьба появляется в хронологии обоих супругов; отдельное событие в `events` для неё не требуется.

Для другого подтверждённого факта добавьте в профиль:

```json
{
  "events": [
    { "id": "event-id", "title": "Название события", "date": null }
  ]
}
```

При наличии документа добавьте `documentId`; для ссылки из массива `sources` профиля используйте `sourceRefs`. Крещение оформляйте отдельным событием в `events`. Календарный стиль исходной записи и пересчёт даты поясняйте в `notes`.

Хронология формируется из данных. Датированные события, включая рождение, сортируются по датам; при вариантах даты используется самый ранний вариант. Событие рождения без даты и вариантов года остаётся первым. События без даты по умолчанию располагаются после датированных событий, перед смертью. Смерть завершает хронологию. Документы с `showInTimeline: false`, а также недатированные или заведомо посмертные документы при известной дате смерти остаются в архиве и разделе «Документальный след».

Рождения всех именных детей автоматически попадают в хронологии родителей, кроме связей с `kind: "adoptive"`. При неизвестной дате рождения событие сохраняется без даты; предполагаемое родство получает соответствующую пометку. Пункты хронологии обозначаются кружками, без нумерации.

Если из воспоминаний известна последовательность, у события с `"date": null` укажите `beforeEventId` — ID последующего события из того же массива `events`. Например, `"beforeEventId": "military-call-up"` помещает работу или переезд перед призывом, сохраняя неизвестную дату. Несколько событий перед одним событием показываются в порядке массива. Неизвестные ссылки и циклы отклоняются проверкой данных; порядок датированных событий задаётся их датами.

Для документа о собственном рождении укажите `birthDocumentId` в профиле, например `{ "id": "petr-mikheev-1889", "birthDocumentId": "petr-paraskeva-births-1889" }`. Ссылка на источник появится внутри события «Рождение», без второго события с названием документа. Аналогично работает `deathDocumentId` для известного события смерти. Документ остаётся в разделе «Документальный след» и в общем архиве. Сопоставление с событием задаётся явно: одинаковый год или упоминание человека в `peopleIds` сами по себе не означают, что документ относится к его собственному рождению. Семейная дата и её точность сохраняются независимо от даты документа.

## 7. Изменить дизайн

`src/styles/tokens.css` содержит смысловые переменные цветов, шрифтов, интервалов, радиусов и размеров древа. `src/styles/themes/classic.css` переопределяет их для текущей темы.

Кнопка «Весь экран» разворачивает древо вместе с поиском, управлением масштабом и легендой. Повторное нажатие или Esc возвращает обычный вид. Используется Fullscreen API; если браузер не поддерживает или отклоняет запрос, древо занимает всё окно сайта. Масштаб и центр просмотра сохраняются при изменении размеров, а диалог родственников доступен в обоих режимах.

Карточки отцовской ветви голубые, материнской — розовые. Их заливки и рамки задают токены `--color-tree-paternal-background`, `--color-tree-paternal-border`, `--color-tree-maternal-background` и `--color-tree-maternal-border`. Цвет определяется принадлежностью к ветви. Легенда над древом показывает подписи из `src/data/tree-branches.json`; цвета применяются также к списку имён до загрузки интерактивного древа.

Карточки супругов на одном уровне соединены горизонтальной линией между их боковыми краями, со значком двух колец посередине промежутка. Для супругов в разных эпохах значок расположен на вертикальном участке линии между колонками. Наведение раскрывает имена супругов, а предполагаемые связи сохраняют пунктир и соответствующую подпись. Значок нарисован средствами CSS; его размеры задают `--tree-marriage-icon-width`, `--tree-marriage-ring-size` и `--tree-marriage-padding`.

Дети с одинаковым набором родителей соединены общей семейной линией. Когда родительская пара находится на одном уровне, а несколько детей — на соседнем уровне ниже, используется одна горизонтальная перекладина между рядами: к ней подходят линии обоих родителей и от неё спускается прямая линия к каждому ребёнку. Этот вариант применяется, если путь свободен от карточек и других семейных соединений. Для разнесённых эпох и препятствий линии родителей сходятся в общий ствол, который разветвляется к детям. Набор родителей берётся только из связей `parent`; брак не добавляет неизвестного родителя. Дети от разных наборов родителей получают отдельные линии. Для единственного ребёнка ствол спускается прямо к его карточке, если путь свободен; при препятствии он проходит в промежутке между колонками. Перекрывающиеся горизонтальные линии разных семей размещаются на разных высотах. Точки отмечают места соединения и ответвления; их размер задаёт `--tree-junction-radius`. Статусы и виды родства сохраняются в сегментах; общий сегмент с предполагаемой или приёмной связью получает соответствующий пунктир.

Для новой палитры и шрифтов меняйте `classic.css`. Для отдельной темы скопируйте его и замените импорт в `global.css`. Данные и функции родства остаются прежними. `global.css` управляет обычными страницами, `components/genealogy/tree.css` — древом. Геометрия карточек берётся из токенов, поэтому изменение размеров сохраняет соединения.

## 8. GitHub Pages

Публикация выполняется только после отдельной команды обновить сайт. Готовый порядок для агента хранится в `docs/publishing.md`; используйте его при работе с текущим репозиторием. Ниже описана первоначальная настройка хостинга.

1. Создайте репозиторий и загрузите содержимое этой папки в его корень: `package.json` и `.github` должны быть в корне. `node_modules`, `dist`, `.tooling` не загружайте.
2. Назовите основную ветку `main`.
3. Откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**.
4. Отправьте изменения в `main`. Workflow установит зависимости из lock-файла, выполнит тесты, проверку данных, сборку и проверку статических ссылок, затем опубликует `dist`.
5. Адрес и результат появятся в **Actions** и **Settings → Pages**. Повторный запуск: **Actions → Deploy family archive to GitHub Pages → Run workflow**.

Настройка получает адрес и путь через `actions/configure-pages`. Поддерживаются `https://USERNAME.github.io/REPOSITORY/` и сайт в корне. Конфигурация Astro использует `site`, `base`, переменные `SITE_URL` и `BASE_PATH`. Ссылки страниц и медиа проходят через единый helper.

Проверка project site локально:

```sh
SITE_URL=https://example.github.io BASE_PATH=/family-tree/ npm run build
BASE_PATH=/family-tree/ npm run preview
```

Откройте `/family-tree/` на адресе preview. Для обычной локальной версии соберите снова без переменных.

Справка: [Astro для GitHub Pages](https://docs.astro.build/en/guides/deploy/github/), [Configure Pages](https://github.com/actions/configure-pages/blob/main/action.yml).

## Проверки и архитектура

Русская версия использует основные адреса сайта, английская — соответствующие адреса `/en/`. Переключатель RU / EN в шапке ведёт на ту же страницу на другом языке. Канонические адреса и ссылки `hreflang` задаются для обеих версий.

Агент синхронизирует английскую версию автоматически после отдельной команды обновить опубликованный сайт. При обычных правках меняются русские исходники; для их проверки используйте `npm run check:ru`. Накопленные переводы агент готовит непосредственно перед публикацией по `docs/publishing.md`, затем проверяет и публикует обе версии вместе.

`npm run build` создаёт английские исходники из общих шаблонов и переводов, затем собирает обе версии. Сгенерированная папка `.tooling/en/` исключена из Git; вручную её не редактируйте. Тексты биографий и документов переводятся в `src/i18n/content.en.json`, интерфейс — в `ui.en.json`, имена и места — в `names.en.json`, руководство — в `developer.en.md`. Отсутствие перевода останавливает двуязычную сборку. Даты, родственные связи, IDs и исходные медиа сохраняются общими. `npm run dev` показывает русские исходники; обе готовые версии доступны после сборки через `npm run preview`.

Блок «Люди и их истории» на главной использует `featuredPeople` из `src/domain/people.ts`. Он выбирает до трёх самых объёмных биографий длиной от 80 слов. Учитывается только текст биографии; заголовки разделов, краткое описание, примечания, источники и даты на отбор не влияют. При равном объёме порядок определяется именем и ID. Если подходящих записей меньше трёх, пустые или краткие страницы не добавляются; при отсутствии подходящих биографий блок скрыт.

Уровни древа сгруппированы по эпохам на основе годов рождения во всех семейных ветвях. Близкие даты объединяются в периоды примерно до 30 лет; родственные поколения помогают выбрать границы. Для неизвестных дат расположение определяется по родственникам. Это только правило раскладки: приблизительные годы не добавляются в семейные данные и хронологию. Супруги с большой разницей в годах рождения могут находиться на разных уровнях. Если известны родительские карточки обоих супругов, их порядок в паре следует расположению родителей, чтобы входящие линии не перекрещивались. Подписи периодов показывают только известные исходные годы.

Корни и подписи горизонтальных областей заданы в `src/data/tree-branches.json`. Состав областей вычисляется по родственным связям, без сопоставления фамилий. Обход не проходит через выбранную пару и её потомков, поэтому брак не смешивает две стороны. Дети показаны под обеими ветвями; если родственник связан с обеими сторонами или его ветвь неизвестна, он получает отдельную область. Возможное совпадение записей не определяет принадлежность к ветви. Разделение областей не меняет уровни по эпохам и статусы предполагаемых связей. Неизвестные корни и повторяющиеся настройки ветвей отклоняются проверкой данных.

Главная линия выбрана в `src/data/tree-view.json` полем `focusPersonId`. На древе остаются выбранный человек, его собственные братья и сёстры, все прямые предки по имеющимся родительским связям и их подтверждённые супруги. Супруги показываются отдельными карточками, даже когда их родительская связь с потомками не установлена. Братья и сёстры предков, кузены и другие боковые родственники раскрываются кнопкой «Родственники» внутри соответствующей карточки. Неподтверждённые супруги и родители супругов, не относящиеся к прямой линии, также остаются внутри карточек. Предполагаемые связи сохраняют свои пометки. Брак сам по себе не добавляет родителя. При открытии древо приближено к ближайшей семье выбранного человека; «Все предки» показывает главную линию целиком. Все записи остаются в исходных данных, общем списке людей и на личных страницах. Неизвестный `focusPersonId` отклоняется проверкой данных.

Главная линия выравнивается по семейным осям: ребёнок расположен под серединой родительской пары, а при одном известном родителе центры карточек совпадают по вертикали. Подтверждённый супруг без родительской связи занимает соседнюю карточку на том же уровне, сохраняя ось фактических родителей. Братья и сёстры размещаются с равными интервалами вокруг общей оси. Расстояния между предками учитывают карточки на каждой эпохе, чтобы пары и их ветви помещались без перекрытий. Отцовская и материнская стороны разделены промежутком. Для древа с боковыми родственниками, общими предками нескольких линий или супругами на разных эпохах используется общая раскладка ветвей.

`npm run validate-data` проверяет исходный формат и профили через Zod, уникальность IDs/slugs, все ссылки на людей/места/документы, согласованность связей, родительские циклы, события браков, форматы дат и наличие указанных медиа. Ошибки останавливают сборку. Замечания об исторических противоречиях сохраняются как данные и показываются пользователю.

`npm run verify-build` проверяет уже собранные HTML: адреса внутри `base`, существование файлов, метаданные и семейные сведения на личных страницах. `npm test` проверяет доменные функции, сохранение исходных данных и раскладку реального графа. Тестовые вымышленные объекты не публикуются.

```text
src/
  data/
    family.json          # Переданный info.json: узлы, связи, замечания
    people/              # Необязательные биографии, фото и уточнения
    documents/           # Один JSON на реальный документ
    places/              # Один JSON на место
  domain/
    schemas.ts           # Zod и типы
    family-source.ts     # Адаптер исходного формата, без UI
    catalog.ts           # Загрузка источника и профилей
    validation.ts        # Целостность данных
    people.ts
    relationships.ts     # Родство, статусы, все виды связей
    source-notes.ts       # Замечания и безымянные родственники
    documents.ts
    timeline.ts
    dates.ts
    urls.ts
  components/
    layout/
    genealogy/           # Изолированный React/SVG движок и раскладка
    person/
    documents/
  pages/
    index.astro
    tree.astro
    people/{index,[slug]}.astro
    documents/{index,[id]}.astro
    404.astro
  styles/{tokens,global}.css
  styles/themes/classic.css
public/media/{photos,documents,sources}/
scripts/                 # Проверка источника, медиа и собранного сайта
tests/
.github/workflows/deploy.yml
```

Четыре слоя разделены: семейные JSON, доменная логика, UI и тема. Исходные связи задаются один раз; адаптер формирует симметричные списки родственников и сохраняет статус каждой связи. React используется только в интерактивном древе. Остальные страницы статические, фильтры работают на небольших скриптах. Движок `GenealogyTree` можно заменить независимо от исходного формата и темы. Документ остаётся одной сущностью для нескольких людей. Astro создаёт полностью статический сайт без базы данных, серверных API и авторизации.
